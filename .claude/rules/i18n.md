# i18n — Translated User-Facing Strings

Every string a client can read — response message, error message, mail subject, validation message — is a **catalog key**, not an English literal. The machinery is hand-rolled and lives entirely in `src/libs/i18n/`; there is no framework i18n package involved.

## Current state: fully wired, as of 2026-08-20

`src/libs/i18n/` is complete and working, `LocalePlugin` is in `baseApp`, and **every module now goes through the translator**: `auth`, `home`, `health`, and all four `settings/*` modules — 81 call sites over 54 distinct keys. `AuthMailService` (`src/libs/mailer/services/auth-mail.service.ts`) uses `t()` for its subjects.

This repo used to be the odd one out: the machinery existed and **no file under `src/modules/` called it**, so the `id` catalogue was unreachable through the API. The catalogues went from 52 to **92 keys** closing that gap, with the new `role.*`, `user.*`, `permission.*`, and `selectOption.*` groups written for this repo (the sibling `clean-elysia` only localizes `auth` and `profile`, so there was nothing to copy).

Two consequences worth knowing:

- **This repo is now ahead of `clean-elysia` on i18n coverage**, not behind. Don't "align" by copying the sibling's narrower catalogue back over this one.
- Following the sibling's `auth/service.ts` idiom, the `BadRequestError` **titles** in auth all resolve to `t("auth.validationError")` ("Validation error") with the specific text carried in the `errors[].message` field array. That changed auth's top-level English error titles from the more specific "Invalid credentials" / "Email not verified". It matches the reference implementation; if the specific titles matter to a client, that is a deliberate decision to revisit, not a bug to patch around.

## Location

- Translators: `src/libs/i18n/i18n.ts`, exported from `@i18n`
- Catalogs: `src/libs/i18n/locales/en.json`, `src/libs/i18n/locales/id.json`
- Generated key union: `src/libs/i18n/locales/keys.generated.ts`
- Generator: `src/libs/i18n/scripts/generate-keys.ts` (`bun run i18n:keys`)
- Locale resolution: `src/libs/i18n/accept-language.ts`, `src/libs/i18n/locale-store.ts`, `src/libs/plugins/locale.plugin.ts`
- Validation messages: `src/libs/i18n/validation.ts`

## Rules

1. **Two entry points, and only two.** `t(key, vars?)` resolves against the current request locale — use it inside a request. `translate(key, vars?, locale?)` takes an explicit locale — use it only where there is no request locale to read (a BullMQ worker, a seed script, a startup log).
2. **`key` is typed `TranslationKey`.** A typo or unregistered key is a compile error, not a silent English fallback. That is the whole point of the generated union.
3. **Alias the import in route files.** `import { t as trans } from "@i18n"` — bare `t` collides with Elysia's TypeBox namespace, which every `index.ts` already imports. Services import plain `t`.
4. **Catalogs are flat maps of dotted keys.**
   ```jsonc
   { "auth.invalidCredentials": "Invalid credentials", "profile.updated": "..." }
   ```
   There is no nesting — the dots are part of the key string. Current groups: `common.`, `errors.`, `auth.`, `profile.`, `validation.`, `mail.`.
5. **Interpolation is double-brace, filled from `vars`.** `t("auth.welcome", { name })` against `"Welcome, {{name}}"`. A placeholder with no matching var is left verbatim as `{{name}}` and ships to the client — which is deliberate, so you notice.
6. **`en` and `id` move together.** A key added to one is added to the other in the same change. This is enforced: `bun run i18n:keys` exits non-zero when `id.json` is missing a key `en.json` has.
7. **Never hand-edit `keys.generated.ts`.** It carries an `AUTO-GENERATED` banner. Touch a catalog, run `bun run i18n:keys`, commit the regenerated file with the catalog change. The pre-commit hook's `tsc --noEmit` will catch you if you don't.
8. **`DEFAULT_LOCALE` is `en`** (`src/libs/i18n/types.ts`) and is the fallback both for an unsupported locale and for a key missing from a supported one.
9. **The locale comes from `Accept-Language` only.** `LocalePlugin` parses it in `onRequest` via `parseAcceptLanguage` (q-value sorted, `en-GB` normalised to `en`, unknown tags to `DEFAULT_LOCALE`) and stores it with `enterLocale`; `getCurrentLocale()` reads it back out of an `AsyncLocalStorage`. There is no `?lang` query or `x-lang` header resolver. Adding one means changing `LocalePlugin`, not faking it at the call site.
10. **The async store does not cross a queue boundary.** A producer captures `getCurrentLocale()` and puts it in the job payload — see `AuthMailService` and [mail.md](./mail.md). For non-request work, wrap with `runWithLocale(locale, fn)`.
11. **Validation messages go through `translateValidationMessage(err)`** (`src/libs/i18n/validation.ts`), which maps a TypeBox error onto `validation.*` keys by checking `err.schema.format` first, then pattern-matching the raw message. Add a constraint it cannot classify, and you add both the key and the branch — see [validation.md](./validation.md).
12. **`profile.*` keys exist with no `profile` module.** They are inherited from the sibling repo. Leave them; do not "clean up" catalog keys as a drive-by, because the generator treats a key present in `id.json` but absent from `en.json` as a warning and the reverse as a hard failure.

## Don't translate

- Log messages. `log.info({ userId }, "Verification email queued")` is always English — logs are read by operators.
- Internal detail: Prisma error codes (`P2002`, …), constraint names, stack traces.
- The field and key names inside a structured error payload. Only the human-readable message string is translated.
- Anything from a repository. Repositories own queries ([repositories.md](./repositories.md)); the message belongs to the service that throws ([services.md](./services.md)).
